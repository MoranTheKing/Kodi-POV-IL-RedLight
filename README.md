# Kodi POV IL — Lab

An experiment, kept deliberately apart from the build people actually use.

Two questions are being tested here, in this order, and the second only matters
if the first comes back yes:

1. **Does Kodi 22 "Piers" work for us at all** — specifically, do FENtastic,
   Estuary and NOX load and render on it?
2. **Could Red Light replace POV** as the video add-on?

Nothing here ships to anyone. The production build lives at
[Kodi-POV-IL](https://github.com/MoranTheKing/Kodi-POV-IL) and is untouched by
anything in this repository.

## Why this is a separate repository

Three reasons, in order of how much they cost if ignored.

**The update channel.** `build.txt` is a single file at a fixed path, and the
wizard reads it to decide what to install. Sharing a repository would mean
sharing that file, so an experimental device and a production device would
resolve the same target. Separate repositories make crossing over impossible
rather than merely unlikely.

**Size.** The production repository's `dist/` is 928 files and 10.65 GB, 1.72
GiB packed — already past what GitHub recommends. It bit us once: a history
rewrite there had to switch from `--tree-filter` to `--index-filter` because
checking out those trees filled the disk. A second build line would make that
worse. This repository holds tooling and no artifact history; it is under 300 KB.

**Blast radius.** An experiment that cannot touch the production channel cannot
break it.

## What must be true before the first build runs

**The package id is `org.xbmc.povr`, and that is not an arbitrary choice.**
Android keys apps by applicationId, which is why a device running stock Kodi
cannot install a second one. The production build already solves this by
rebranding to `org.xbmc.povi`. Reusing *that* id here would make this experiment
**replace** the maintainer's working install instead of sitting beside it. So:

| id | app |
| --- | --- |
| `org.xbmc.kodi` | stock Kodi |
| `org.xbmc.povi` | Kodi POV IL (production) |
| `org.xbmc.povr` | this |

The id must stay **13 characters**. The build patches the package-id strings
inside Kodi's DEX and native libraries in place; the bytes are replaced, not
relocated, so a different length corrupts the APK. The workflow refuses to run
if the lengths differ.

**Signing is not set up yet, and it is the one thing that needs a decision.**
The workflow needs a `KEYSTORE_PASSWORD` repository secret and a
`.secrets/release.keystore.enc` file. There are two ways to get them and they
are not equivalent:

- *Copy the production key.* One identity to manage. But the production signing
  key then exists in a second repository, and an experiment is exactly the kind
  of place where things get shared more casually.
- *Generate a fresh key here.* The experimental app gets its own identity and
  the production key never leaves the production repository. The cost is that
  this app can only ever be updated with this key — which is fine, it is a new
  app. **This is the recommended option.**

Either way the two apps coexist on a device regardless of key, because Android
separates them by package id, not by signature.

## What the first build deliberately does NOT include

No Red Light, no wizard, no build hydration, no add-ons. Just Kodi 22 under a
different name, with the icon and banner swapped.

That is not laziness. If the skins do not come up on Piers there is nothing to
port, and every hour spent on the other 132 `plugin://` references would be
wasted. The full inventory of what a port would have to preserve — 48 files and
965 Hebrew lines across five skins — is generated by
`tools/skin_customisation_inventory.py` in the production repository.

## What is already known about Kodi 22

Checked against Kodi's own source at tags `21.3-Omega` and `22.0b1-Piers`,
because the Kodi forum is unreachable from CI:

```
xbmc.gui         5.17.0 -> 5.18.0
                 <backwards-compatibility abi="5.17.0"/>
control types    28 -> 28     nothing removed
builtins         nothing removed; loadskin and playplaylist added
info labels      6 removed, 62 added -- none of the 6 reaches our skins
```

The back-compat line is what decides whether a 5.17.0 skin loads, and all four
skins here are 5.17.0. So nothing *structurally* blocks them.

What that does not cover is rendering, which is where the reports of "some
skins leave the interface unresponsive" live, and which is the entire reason
this APK exists. Kodi 22 could not be run in CI to check: the Team Kodi PPAs
are stale (newest is a Kodi 21 nightly from 2023, nothing for Ubuntu 24.04) and
building from source is not viable there.

## Running it

Actions → **Build the Kodi 22 test APK** → Run workflow. It produces a 32-bit
and a 64-bit APK as a build artifact. Install beside what you already have.

The Piers 32-bit APK lives under `arm/` on the mirror, not `armeabi-v7a/`,
while the file inside is still named `armeabi-v7a`. The workflow already
accounts for that; it is written down because it is the kind of thing that
looks like a broken URL.
